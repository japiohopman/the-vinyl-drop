# Branded Error and Failure-State References

This folder maps actual application-handled error templates and failure states. It must not imply that every HTTP status has a separate EJS page.

## Current application templates

| Reference | Actual source | Current behavior |
| --- | --- | --- |
| `400-desktop.png` / `400-mobile.png` | `views/errors/400.ejs` | Generic HTML response for application-handled 4xx statuses other than 404; includes a status-specific heading/message. Many validation problems instead stay inline in their owning form. |
| `404-desktop.png` / `404-mobile.png` | `views/errors/404.ejs` | Branded “Not in this crate” recovery page for unknown routes, unavailable listing/profile and the HTML messaging-disabled guard. It uses the original empty-sleeve SVG, Browse and Home links, and retains HTTP 404. |
| `500-desktop.png` / `500-mobile.png` | `views/errors/500.ejs` | Branded “We hit a skip” recovery page for Express-handled 5xx responses, including forwarded 502/503/504 statuses. The actual numeric status is shown and retained. A same-path retry is available only for GET requests and omits query data. |

## Failure states that are not separate branded HTML pages today

| Status / state | Current behavior | Reference treatment |
| --- | --- | --- |
| 401 | Protected page flows normally redirect to sign-in; API handlers may return JSON. Generic HTML errors use the shared 400 template. | Do not create a dedicated 401 baseline unless a real HTML route is introduced. |
| 403 | Generic error handler uses `400.ejs`; a few listing controller ownership branches currently use `500.ejs` while preserving status 403. | Record as a current implementation inconsistency; any dedicated visual needs a separate implementation issue. |
| 429 | Shared rate limiter returns plain text or JSON with `Retry-After`. Contact's own email cooldown re-renders Contact at 429. | Capture the Contact inline state only if needed; no standalone 429 HTML baseline exists. |
| 503 | Shared rate-limit infrastructure failure returns plain text or JSON; Contact provider failure renders the Contact form at 503. Generic errors passed to Express can use `500.ejs`. | No single standalone 503 screen exists today. |
| 502 / 504 | No dedicated application route/template. Commonly generated by a reverse proxy or hosting layer before Express. If forwarded through Express, the generic 500 view is used. | Hosting-owned branded error pages are out of scope unless the actual deployed layer supports custom error documents. |
| 505 | No application route or dedicated view. HTTP-version rejection is ordinarily owned by the edge/server before Express. | Do not create a fake 505 page or screenshot. Only revisit if Render/Cloudflare exposes a supported custom error-page mechanism. |

## Capture and update rules

- Capture redesigned 404/500 states only after their separate UI implementation exists and can be reached through a safe, reproducible test state.
- Never force a production or staging outage or corrupt a live request to obtain a 500 screenshot. Use a controlled test fixture/isolated test path if a reproducible capture is added later.
- Keep the HTTP status truthful; visual polish must not turn an error into HTTP 200.
- Do not expose stack traces, SQL, credentials, provider internals or arbitrary exception messages.
- Record route/state, viewport, theme, capture date and deployed app SHA when known.
- Update the corresponding reference and central index in the same implementation PR.
